## 開発者体験を良くするとき、いちばん熱が入る

コードを書く人の手元が楽になると、チーム全体の速度も変わる。そういう話を、いつもより具体的に感じられる場面がある。

ローカルで検証に詰まっていたフローを整えて、誰でも同じ手順で起動できるようにしたとき。LLM を前提にした開発フローに合わせて、仕様やコンテキストの扱いを見直したとき。ツールや README を直しただけなのに、チームの会話のトーンが変わったとき。

そういう瞬間に、いちばん熱が入る。

[2025 年を振り返る](/ja/life/reflections-on-2025/) で書いた [Google Cloud Next '25](https://cloud.withgoogle.com/next/25) でも、拙い英語で必死に伝えたのは同じことだった。「開発者体験の向上こそが、最大の喜びであり、やりがい」だと。

現職ではプリセールスやチームリードも任されている。営業と一緒にお客様の課題を聞く時間も、メンバーと 1on1 する時間もある。どちらも、案件チームの中で開発者体験を整える動きと矛盾しない。むしろ、現場の詰まりを知っているからこそ、手を入れられる場面もある。

## その時々に合うものを選ぶ

開発手法は案件ごとに違う。LLM の使い方も、チームや時期で変わる。

だから、開発者体験を良くするときも、毎回同じやり方である必要はないと思っている。既存の OSS で足りるならそれを使う。社内の文脈に合わないなら、合う形で作る。どちらも同じ方向への投資だ。

「自分で作らなければ」というより、「その時々の開発にとって最適なものを、チームに届ける」方が近い。

## 社内 — process-compose を採用した

案件チームのローカル開発・検証では、同じボトルネックが何度も繰り返されることがある。

複数のプロセスを立ち上げる。依存関係の順序を守る。README に書いてある手順を、毎回人が追う。新人が入ったとき、環境構築だけで半日消える。こういう詰まりは、機能の複雑さそのものより、開発体験の設計でかなりの部分を占める。

そこで [process-compose](https://github.com/F1bonacc1/process-compose) を使った。F1bonacc1 氏の OSS で、非コンテナのアプリケーションを YAML で定義し、起動順序や依存関係をまとめて orchestrate できる。Go 製の単一バイナリで、Dockerfile や volume、ネットワーク定義を扱わずに済む場面も多い。

自分の OSS ではない。それでも、ローカル開発の繰り返しを減らすには十分だった。`process-compose.yaml` に起動手順を集約し、TUI や CLI からプロセスの状態を見ながら開発できるようにした。README の長い手順を、起動コマンド一つに寄せられた。

「開発者体験を良くする」とき、必ずしも新しいリポジトリを作る必要はない。既に良い道具があるなら、それをチームの文脈に合わせて取り込む。process-compose はその一例だ。

## 社内 — contextlint を使わせた

[contextlint](https://contextlint.dev) は自分で作っている。Markdown や仕様書の整合性を lint するツールで、LLM 前提の開発フローと相性がいい。

社内でも使わせた。仕様書と実装のズレ、AI に渡すコンテキストの粒度、レビュー前のチェック——開発の進め方によって必要なガードレールは変わる。contextlint は、その文脈に合わせてルールを定義できる。

評判は良かった。ツール単体の話というより、「こういう開発の進め方なら、こういうチェックがあると楽」という提案として受け取ってもらえた感覚がある。

合う OSS があるならそれを使う。なければ、社内の開発の仕方に合わせて作る。contextlint は後者の例だ。

## TerraDart — 個人開発を超えつつある

[TerraDart](https://terradart.dev) は、Go / Flutter スタック向けに Dart で型安全な IaC を書く pre-alpha の試み。GCP リソースを Dart で型付きに記述し、標準的な `*.tf.json` を出力する。既存の `terraform apply` パイプラインはそのまま使える。

もともとは個人開発として始めた。いまは Google の Go / Flutter プロダクトマネージャとフィードバックをもらいながら進めている。設計の方向性、開発者にとっての使い心地、エコシステムとの接続——個人のリポジトリだけでは届かない視点が入ってきた。

個人開発というより、外の目も入った、もう一段大きな取り組みになってきている。開発者体験を良くする、という軸は変わらない。Terraform を書く人が、Dart / Flutter の文脈から IaC に触れられるようにしたい、という動機も同じだ。

詳しくは [terradart.dev](https://terradart.dev) や別の機会に書く。ここでは、いま自分がいちばん時間をかけているもののひとつ、という位置づけだけ置いておく。

## いまのやり方

開発者体験を良くするための設計や実装では、LLM と壁打ちする時間が増えた。一から設計を考え、推奨案に対して「このチームの文脈だとここが足りないのでは」と返す。全部を任せるのではなく、届け先が人間である以上、判断が必要な部分を自分で持つ。

OSS であれば、利用者側の体験とメンテナー側の体験の両方がある。社内の仕組みであれば、オンボーディングのしやすさや、日々の運用コストが効いてくる。記事や登壇資料であれば、誰にどの深さで伝えるか。こういった軸は、まだ機械が一括で最適化してくれる領域ではない。

---

開発者体験を良くするとき、いちばん熱が入る。process-compose のように既存の OSS を採用するときも、[contextlint](https://contextlint.dev) のように社内に合わせて作るときも、[TerraDart](https://terradart.dev) のように個人の枠を超えて育てていくときも、根っこは同じだ。

それが、いまの自分の現在地だ。
