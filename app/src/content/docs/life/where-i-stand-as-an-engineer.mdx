## Developer Experience Is Where I Feel the Most Energy

When life gets easier for the people writing code, the whole team moves differently. I feel that most clearly in concrete moments.

Untangling a local verification flow so anyone can start it the same way. Rethinking how specs and context are handled for a workflow built around LLMs. Fixing a tool or a README and watching the tone of team conversation shift.

That's when I feel the most energy.

As I wrote in [Reflections on 2025](/life/reflections-on-2025/), at [Google Cloud Next '25](https://cloud.withgoogle.com/next/25) I said the same thing in broken English: improving developer experience is my biggest joy and where I find the most meaning.

At my current job I also do pre-sales and team leadership. Time with sales hearing customer problems, and weekly 1-on-1s with my reports, doesn't conflict with improving developer experience inside project teams. If anything, knowing where the friction is makes it easier to know where to act.

## Choosing What Fits the Moment

How a team builds changes from project to project. How LLMs are used changes with the team and the season.

So when I'm improving developer experience, I don't think the answer always has to be the same. If existing OSS is enough, use it. If it doesn't fit the internal context, build something that does. Both are investments in the same direction.

It's less "I have to build it myself" and more "get the best fit for how this team develops right now."

## At Work — Adopting process-compose

On project teams, the same bottlenecks in local development and verification tend to repeat.

Spin up several processes. Respect dependency order. Follow steps in a README by hand, every time. A new teammate loses half a day just getting the environment running. A lot of that friction comes from how developer experience is designed—not from the complexity of the feature itself.

That's where I used [process-compose](https://github.com/F1bonacc1/process-compose). It's OSS by F1bonacc1: define non-containerized applications in YAML and orchestrate startup order and dependencies together. A single Go binary—often without dealing with Dockerfiles, volumes, or network definitions.

It's not my OSS. It was still enough to cut the repetition in local development. We consolidated startup in `process-compose.yaml` and made it possible to develop while watching process state from the TUI or CLI. Long README steps collapsed toward a single startup command.

Improving developer experience doesn't always mean opening a new repository. When a good tool already exists, bring it into the team's context. process-compose is one example of that.

## At Work — Putting contextlint to Use

[contextlint](https://contextlint.dev) is something I built—a linter for consistency in Markdown and specs that fits well with LLM-driven development workflows.

I also put it to use internally. Drift between specs and implementation, the granularity of context passed to AI, checks before review—the guardrails you need change with how development is run. contextlint lets you define rules for that context.

The reception was good. Less "here's a tool" and more "if you're developing this way, these checks make life easier."

Use OSS when it fits. Build when the team's way of working needs something shaped for it. contextlint is the latter.

## TerraDart — Growing Beyond a Personal Project

[TerraDart](https://terradart.dev) is a pre-alpha attempt at type-safe IaC in Dart for the Go / Flutter stack. Author typed GCP resources in Dart, emit standard `*.tf.json`, and keep your existing `terraform apply` pipeline.

It started as a personal project. Now I'm moving it forward with feedback from Google's Go and Flutter product managers. Design direction, how it feels for developers, how it connects to the ecosystem—perspectives I couldn't get from a solo repository are coming in.

It feels less like a side project and more like something larger, with outside eyes on it. The axis hasn't changed: I want to improve developer experience. The motivation is still to let people who work in Dart / Flutter reach IaC from that context.

I'll write more on [terradart.dev](https://terradart.dev) and elsewhere. For this post, it's enough to say it's one of the things I'm spending the most time on right now.

## How I Work Now

When I'm designing or building for developer experience, I spend more time sparring with LLMs. Think through the design from scratch, push back on recommendations with things like "in this team's context, isn't something missing here?" I don't hand everything over—as long as the audience is human, some judgments still need to stay human.

For OSS, there's the experience of users and maintainers. For internal tooling, onboarding and day-to-day operating cost matter. For posts and talks, who you're talking to and how deep to go. Machines don't optimize all of that in one shot yet.

---

Developer experience is where I feel the most energy. Whether that means adopting existing OSS like process-compose, building for how a team works like [contextlint](https://contextlint.dev), or growing something past the personal-project frame like [TerraDart](https://terradart.dev), the root is the same.

That's where I stand today.
